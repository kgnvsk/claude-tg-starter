# Оновлення Novsky Starter

Єдине підтримуване джерело оновлень — `https://github.com/kgnvsk/claude-tg-starter.git`.

Ми публікуємо новий комплект у GitHub і в архіві. Публікація не запускає
оновлення встановлених агентів. Власник за бажанням передає своєму агенту
посилання або архів і просить оновитися зі збереженням памʼяті, налаштувань
та доступів. Агент перевіряє випуск і застосовує його у своїй установці.

Ця інструкція стосується **Claude Code**. Для Codex читай
`codex/UPGRADING.md` у комплекті; не запускай Claude `update.sh` для Codex.
Конфлікт із власними змінами не дозволяє їх стерти. Оновлення Novsky має
окремий канал і не є командою оновити всіх агентів.

Повний установщик потребує прав адміністратора сервера. Telegram-агент без
цих прав готує перевірку й план для адміністратора; отримання кита саме по
собі не надає додаткових прав і не означає, що оновлення вже застосовано.

## Перевір спочатку ZIP-оновлення: лише той самий продукт

Ця точка входу виконує **узгодження того самого продукту** для
`starter` (Novsky Starter). Це не перевстановлення й не
міграція. Заявленим джерелом оновлень архіву має бути
`https://github.com/kgnvsk/claude-tg-starter.git`.

### 1. Перевір архів, перш ніж торкатися сервера

Прочитай ці файли з нового архіву саме в такому порядку:

1. `RELEASE.json`
2. `PRODUCT.json`
3. `UPDATE_CHANGELOG.md`
4. `UPGRADING.md`
5. `VERIFY.md`

Вимагай повний, незмінений архів із узгодженими metadata релізу й продукту.
Відхиляй відсутній файл, некоректну ідентичність, неочікуване символьне
посилання чи будь-який збій перевірки цілісності. `productId` архіву має
точно дорівнювати `starter`.

### 1a. Класифікуй керовані файли до будь-якої мутації

Визнач абсолютний шлях до перевіреного нового архіву як `STAGED_KIT`, а потім
від імені `claude` виконай read-only план:

```bash
runuser -u claude -- "$STAGED_KIT/assets/bin/update-safety-check" plan   --home /home/claude   --kit "$STAGED_KIT"   --policy "$STAGED_KIT/assets/product/managed-runtime.json"   --baseline /home/claude/.claude/product/managed-runtime-baseline.json   --owner claude   --json
```

`managed-runtime-baseline.json` містить hashes останньої прийнятої версії
комплекту після підстановки профілю конкретного агента, а не hashes сирих
шаблонів чи поточних живих файлів. Тому трьохстороннє порівняння
відрізняє зміну власника від зміни нового комплекту. Наприклад, локальну Whisper
замість OpenAI API треба автоматично зберегти, якщо новий комплект не змінював
той самий файл. Якщо обидві версії змінили той самий шлях, план має завершитися
зі статусом `blocked` до будь-якої мутації. Не роби копій `.my`, не відновлюй
файли поверх нового комплекту вручну й не підмінюй контрольну базу живими
hashes.

Для legacy-інсталяції без контрольної бази спочатку збережи й перевір старий
довірений kit у `TRUSTED_OLD_KIT`. Лише якщо його `productId` збігається з живим
продуктом і він є точною встановленою версією, одноразово виконай:

```bash
runuser -u claude -- "$STAGED_KIT/assets/bin/update-safety-check" seed   --home /home/claude   --kit "$TRUSTED_OLD_KIT"   --policy "$TRUSTED_OLD_KIT/assets/product/managed-runtime.json"   --baseline /home/claude/.claude/product/managed-runtime-baseline.json   --owner claude   --json
```

Після `update-safety-check seed` повтори `update-safety-check plan` проти
`STAGED_KIT`. Якщо старої точної версії немає або план заблокований, зупинися й
попроси ручний diff/merge; не запускай installer/update.

Installer застосовує керовані файли з відкладеним оновленням контрольної бази й
приймає новий baseline лише після успішних `memory-doctor` та `skill-doctor`.
Тому не записуй baseline вручну між застосуванням файлів і фінальними
перевірками.

### 2. Досліди живу інсталяцію лише для читання

До будь-якої зміни перевір власника файлів, символьні посилання, стан Git,
службу й drop-ins, процеси, transport, managed drift, вільне місце та metadata
встановленого продукту. Визначай живий `productId` за
`/opt/claude-tg-starter/PRODUCT.json`, якщо файл існує. Для legacy
installation відсутній кореневий файл дозволено лише тоді, коли
`/home/claude/.claude/product/runtime.json` або
`/opt/claude-tg-starter/assets/product/runtime.json` однозначно визначає той
самий продукт. Суперечливі metadata або невідповідність productId — жорстка
зупинка.

Автоматичне узгодження підтримує рівно таку канонічну топологію:

- HOME агента — `/home/claude`, і це не спільний HOME;
- збережена конфігурація — `/etc/claude-tg-starter/agent.env`;
- `claude-telegram.service` працює від користувача `claude` зі стандартним
  transport;
- працює рівно один стандартний Bun poller, без другого процесу Claude.

Неканонічна топологія має зупинити процес до будь-якої зміни. Зупиняйся через
кілька instances, нестандартного користувача, нестандартну службу, daemon
transport, брудний чи сторонній kit або символьне посилання, а також managed
customization, що перетинається з керованим шляхом. Керовані власні правки
потребують явного diff/merge; якщо безпечне злиття не доведено, зупинися й
запроси ручне узгодження. Ніколи не запускай другий інтерактивний процес Claude
на живому боті.


### 3. Збережи стан і створи резервні копії обох типів

Збережи сховище власника, пам’ять, цілі, секрети, правила доступу Telegram,
groups/admins, створений власником `CLAUDE.md`, власні skills/plugins/hooks
власника та некерований cron. Не виводь секрети або вміст environment.

До зміни служби чи живого комплекту виконай від `claude`
`agent-backup create` і `agent-backup verify`, щоб отримати перевірену
резервну копію без секретів. Створи один managed-work inventory з поточного й
цільового runtime manifests. Зістав поточні й цільові managed
runtime/manifests, стан systemd unit/timer, cron і таблицю процесів, щоб
inventory містив кожне кероване комплектом або продуктом завдання, worker і
довготривалу допоміжну службу, включно з ig-webhook і модулями продукту. Запиши
ідентифікатор кожної служби чи процесу, trigger і поточні стани ввімкнення,
активності та розкладу.

Окремо створи **точний root-only snapshot для відкату** живого комплекту,
конфігурації, systemd unit і drop-ins, cron та managed runtime state. Формуй
його з **точного restore manifest**, створеного до будь-якої зміни. Для кожного
шляху, який цільовий updater може створити, замінити або видалити, запиши факт
наявності чи відсутності, а також SHA-256, тип файла, ціль символьного
посилання, mode, власника й групу. Додай:

- живий kit, збережену конфігурацію та цільові managed manifests;
- `/home/claude/bin` і керовані комплектом
  `/home/claude/.claude` skills, plugins, persona, settings, runtime, index і
  state;
- керований runtime Telegram і preimage схеми `messages.db`, використовуючи
  транзакційно узгоджену резервну копію бази даних, де це доречно;
- systemd units/drop-ins, sudoers, cron і timers;
- усі глобальні інсталяції Claude Code та Codex: package prefixes, identities
  package manager, точні версії, resolved binaries і hashes.

Для кожного глобального CLI захопи відновлюваний package payload або cache й
доведи в ізольованому readback, що він відтворює записані prefix, version,
binary та hash без зміни живої інсталяції. Точний snapshot може містити
секрети: зберігай його лише для root і не надсилай у чат чи звичайні журнали.

Незалежно перевір точний snapshot на цілісність, повноту, permissions і readback
до будь-якої зміни. Переглянь snapshot archive або manifest, підтвердь наявність
кожного потрібного шляху комплекту, конфігурації, systemd/drop-in, cron і
managed state, прочитай захоплені дані, перевір локально записані hashes та
підтвердь, що snapshot і його manifest доступні лише root. Якщо будь-якої
можливої цілі зміни немає в manifest або її не можна відновити ізольовано, це
не точний rollback. Збій перевірки snapshot — жорстка зупинка: не створюй
блокування перезапуску, не зупиняй службу й не торкайся живого комплекту.

### 4. Безпечно підготуй нову версію, а потім увійди в maintenance

Розпакуй повний архів поза живим шляхом і перевір staged tree до використання.
НІКОЛИ не розпаковуй і не копіюй архів як overlay поверх живого комплекту.
Відхиляй символьне посилання, ознаки підміни, неочікуваний файл або невдалу
перевірку.

Novsky Starter безкоштовний: ключ покупки не потрібен. Команда
`bash "$STAGED_KIT/update.sh" --license-preflight` завершується без звернення
до сервісу активації й без зміни працюючого агента.



Створи `/home/claude/logs/restart-hold.until` атомарно як звичайний файл без
символьних посилань, що належить `claude:claude`, із mode `0600` і коректним
майбутнім Unix timestamp.
Використовуючи перевірені restore manifest і managed-work inventory, захопи
точний попередній стан увімкнення, активності та розкладу, а потім **вимкни кожен
керований комплектом cron entry, systemd timer і worker trigger**. Це включає
healthcheck, `/unstick`, limit recovery, relogin/auth rescue та керовані
продуктом jobs. Блокування перезапуску має змусити `/unstick` відмовитися від зміни, а
не змагатися з оновленням.

Після вимкнення кожного trigger коректно зупини або дочекайся завершення кожної
працюючої managed job і довготривалої auxiliary service, включно з ig-webhook і
модулями продукту. Якщо будь-яку managed job або auxiliary service не вдається
зупинити чи завершити, виконай жорстку зупинку без застосування оновлення.
Lifecycle lock barrier охоплює лише учасників lifecycle lock; це додаткова
перевірка завершення, а не доказ тиші допоміжних служб.

Захоплюй lifecycle lock лише як обмежений barrier завершення: дочекайся
завершення кожної активної lifecycle job і зупинися, якщо barrier не вдається
отримати. Утримуючи barrier, виконай
`systemctl stop claude-telegram.service` і підтвердь зупинку служби та Bun
poller. Звільни lifecycle lock одразу після зупинки служби. За станом systemd і
процесів доведи, що не працює жоден керований комплектом або продуктом worker
чи auxiliary service. Перевір, що до зміни живого дерева не залишилося watcher,
updater, doctor, auth helper або другого процесу Claude. Онови й повторно
перевір preimage бази Telegram із зупиненого runtime, щоб жодне прийняте
повідомлення не потрапило між резервною копією та quiescence. Невдале оновлення
preimage — жорстка зупинка. Не утримуй lifecycle lock під час оновлення.
Залишай увесь managed scheduling вимкненим під час перевірки оновлення й
будь-якого rollback. Залишай кожну auxiliary service вимкненою до перевірки
основного Telegram poller однією відповіддю. Службу має бути зупинено до
запуску будь-якого Claude CLI doctor або updater.


### 5. Узгодь підготовлений комплект

Збережи старий kit в унікальному root-only rollback path, а потім атомарно
поміняй перевірений staged kit із `/opt/claude-tg-starter`. Лише після
проходження всіх попередніх перевірок запусти цільовий updater із нового живого
комплекту у transaction-owned maintenance mode:

```bash
CLAUDE_UPDATE_MAINTENANCE=1 bash update.sh
```


Цей режим використовує вже перевірену staged revision і не допускає живої Git
authentication або pull. Він не змінює quiesced crontab, готує optional modules
без активації та залишає основну службу зупиненою. Узгоджуй лише
manifest-managed state й ніколи не перезаписуй збережений стан власника.

### 6. Доведи результат у живій системі

Для перевірки запусти рівно один канонічний primary poller. Maintenance updater
не мав його запускати: спочатку підтвердь, що служба зупинена й Bun poller
відсутній; якщо служба активна, вважай це невдалою перевіркою й не запускай
другу. Потім зовнішня maintenance-транзакція рівно один раз виконує:

```bash
systemctl start claude-telegram.service
```

Якщо команда не спрацювала або з’явився не один poller, другий Claude,
Telegram `409` чи concurrent polling, залиш scheduling і auxiliary services
вимкненими, не видаляй hold і переходь до відкату.

Тепер запусти root-safe strict check саме так:

```bash
runuser -u claude -- /home/claude/bin/onboarding-status --strict
```

Перевір metadata релізу й продукту, product/skill/memory doctors, збережений
стан власника, активну службу та журнали. Потім надішли один реальний запит у
Telegram і вимагай рівно одну відповідь від оновленого агента. Самого стану
systemd active недостатньо. Не повідомляй про
успіх, доки ця реальна перевірка й усі перевірки збереження не пройдуть.
Залишай scheduling вимкненим, а блокування перезапуску чинним протягом цієї перевірки.

Лише після успішної відповіді від одного poller узгодь збережені роботи,
вибрані і поточним, і цільовим станом, із цільовими визначеннями та попередньою
політикою ввімкнення, активності й розкладу. Роботи лише з цільового стану
підкоряються цільовій політиці; роботи лише з поточного стану залишаються
виведеними з експлуатації. Віднови scheduling останнім, перевір отримані
auxiliary services і schedules за захопленими inventory та target manifest, а
потім видали hold і повідом про успіх. Повний попередній стан відновлюється
лише під час rollback.

### 7. Відкоть кожну невдалу перевірку

Після будь-якої невдалої перевірки застосування або результату залишай весь
managed scheduling вимкненим і зупини новий runtime. Атомарно віднови старий
kit та кожен запис manifest, включно із записаною відсутністю, збереженою
конфігурацією, managed runtime, preimage бази Telegram,
systemd/drop-ins/sudoers і `/home/claude/bin`. Віднови записані package
prefixes, точні версії, binaries і payloads Claude Code/Codex, а потім перевір
відновлені hashes, modes, owners і groups до запуску рівно одного канонічного
primary poller та повторення реальної перевірки запиту й відповіді в Telegram.
Для цієї перевірки залишай auxiliary services і schedules вимкненими. Після її
успіху віднови точний попередній стан увімкнення й активності допоміжних служб, а потім
останнім віднови точний попередній scheduling і перевір обидва стани за
inventory до видалення hold. Зберігай старий kit та обидві резервні копії, доки
не пройде кожна перевірка rollback.


## Міграція наявної інсталяції Premium

Цей явний перехід ідентичності відокремлений від перевірки рівності продукту,
але має увійти до **тієї самої транзакції від резервної копії до quiescence**,
описаної вище. Перевір обидві ідентичності, вимагай канонічне чисте джерело
Premium, створи й перевір обидві резервні копії та точний restore manifest,
установи блокування перезапуску й переконайся, що весь керований комплектом scheduling
вимкнено. Заверши активні роботи з lifecycle lock, зупини службу, звільни lock
і доведи, що службу та живий poller зупинено. Жоден живий poller не може
працювати під час quiescence, змін міграції або застосування updater. Керовані
workers і допоміжні служби також залишаються вимкненими протягом цих етапів.

Лише після цих перевірок можна викликати `scripts/clone-product.sh` із
дистрибутива цього продукту з `--migrate-from-premium`. Helper готує новий
checkout поруч із живим шляхом, атомарно міняє їх місцями та зберігає старе
дерево як `/opt/claude-tg-starter.premium-backup.*`. Поки scheduling
залишається вимкненим і живого poller немає, запускай цільовий updater лише в
цій захищеній транзакції:

```bash
cd /opt/claude-tg-starter
CLAUDE_UPDATE_MAINTENANCE=1 bash update.sh
```

Для перевірки або відкату запусти рівно один канонічний poller, поки всі
допоміжні служби й керовані triggers залишаються вимкненими. Надішли один
реальний запит у Telegram і вимагай рівно одну відповідь; використовуй той
самий poller і ніколи не запускай другий.

Updater узгоджує навички, plugins, допоміжні інструменти, необов’язкові модулі й
керований role prompt. Перевір живу Telegram-відповідь, перш ніж видаляти
каталог `premium-backup`, а потім віднови попередній scheduling останнім, як
вимагає транзакція.

Оновлення збіжне: воно зберігає дані й секрети власника у
`/home/claude` та `/etc/claude-tg-starter`, узгоджуючи лише керований
комплектом runtime state. Явно підтримувана міграція Premium-to-role не
дозволяє міграцію role-to-role або role-to-Premium.
